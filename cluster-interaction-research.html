一、执行摘要

Statuz 的 Rust 图引擎（statuz-core）在算法层已经完全实现并可工作——图引擎、Cluster 容器、Field 子图、Bridge 跨字段桥接、存储格式（msgpack + blake3 + argon2）、五大核心查询（traverse / impact / path / subgraph / validate）均有完整实现和单元测试覆盖。自测通过 11 个阶段约 70 个断言。

然而，引擎就绪并不意味着用户可用。当前 CLI 与引擎之间存在严重的交互断层：init 命令创建的 Cluster 仅存在于内存中，进程结束即丢失；save 命令使用硬编码的演示数据（build_test_cluster()），与 init 创建的对象毫无关联；不存在任何添加节点、创建字段、添加边或执行查询的 CLI 命令。交互示例文件 statuz交互示例.md 是一个 0 字节空文件——交互设计处于完全空白状态。

核心结论：问题不在于"如何造出屌炸天的 Cluster"，而在于如何让用户通过 CLI 把项目信息存进去并查出来。引擎 API（Cluster::new, register_node, create_field, add_bridge 等）已经完整可用，缺口完全在 CLI 交互层。

本报告调研了五种交互方式（纯 CLI CRUD、交互式 REPL、文件驱动导入、Dashboard Web UI、自然语言 Describe→Discover→Confirm），分析了它们在实现成本、用户体验、原型适配度和长期价值四个维度上的权衡。推荐方案为分阶段推进：Phase 1 实现 CLI CRUD 命令 + 修复 init/save 链路（1-2 天）；Phase 2 增加 JSON 批量导入（1 天）；Phase 3 增加交互式 REPL（2-3 天）；Dashboard 推迟到引擎交互验证完成后。

三个伴随 crate（arrow-map, niche, syn）均只有 7 行占位代码——一个返回 &'static str 的 placeholder() 函数。它们对应的理想化交互能力（自然语言→图翻译、语义解释、变更提案守门）目前完全不存在。

2.4 Dashboard：不存在

三、问题定义：七个关键缺口

通过对比引擎 API 与 CLI 命令，识别出以下七个阻碍用户创建和使用 Cluster 的关键缺口：

缺口 1：init 不持久化

statuz init --name "My Project" 在内存中创建 Cluster 对象并打印信息，但不写入任何文件。进程结束后 Cluster 丢失。用户无法保存自己创建的 Cluster。

缺口 2：save 使用硬编码演示数据

statuz save --output project.stz 调用 build_test_cluster() 函数，该函数返回一个包含 7 个节点、2 个字段、1 个桥接的硬编码演示 Cluster。用户无法保存自己通过 init 创建的 Cluster。

缺口 3：init 与 save 之间无连接

这是缺口 1 和 2 的直接后果。init 创建的 Cluster 对象不会以任何形式传递给 save。两个命令各自独立运行，没有共享状态。

缺口 4：无节点/字段/边/桥接的添加命令

引擎 API 提供了 register_node(), create_field(), add_bridge(), 以及 GraphEngine 的 add_node() / add_edge()，但 CLI 没有暴露任何这些操作。用户无法通过命令行向 Cluster 添加内容。

缺口 5：无查询命令

五大核心查询（traverse, impact, path, subgraph, validate）在引擎层完整实现，但 CLI 没有任何命令调用它们。用户无法通过命令行查询 Cluster 内的拓扑关系。

缺口 6：无交互式模式

所有 CLI 命令都是一次性的——执行一次即退出。不存在 REPL（Read-Eval-Print Loop）或交互式 Shell，用户无法在一个会话中连续操作 Cluster。

缺口 7：ID 生成不一致

init 使用 format!("cluster-{}", uuid::Uuid::new_v4()) 生成 Cluster ID，而存储模块提供了 generate_cluster_id()（基于 blake3 内容寻址哈希）。两者不一致，且 Cargo.toml 中未声明 uuid 依赖（可能是编译错误或 workspace 隐式依赖）。

缺口映射：缺口 1-3 是链路断裂（init→save 不通），修复后用户可以创建并保存空 Cluster。缺口 4-5 是功能缺失（无 CRUD、无查询），修复后用户可以填充和查询 Cluster。缺口 6 是体验优化。缺口 7 是一致性修复。

四、交互方式选项分析

本节分析五种可能的 Cluster 创建交互方式，从实现成本、用户体验、原型适配度和长期价值四个维度进行评估。

选项 A：纯 CLI CRUD 命令

每个操作是一个独立的 CLI 子命令，通过 --path 指定 .stz 文件，命令执行时加载→修改→保存。

# 创建并保存 Cluster
statuz init --name "My Project" --output project.stz

# 添加字段
statuz add-field --path project.stz --id arch --name "System Architecture"

# 添加节点
statuz add-node --path project.stz --id api-gateway --type service --label "API Gateway"
statuz add-node --path project.stz --id auth-service --type service --label "Auth Service"

# 在字段内添加边
statuz add-edge --path project.stz --field arch \
  --from api-gateway --to auth-service --relation depends-on

# 查询
statuz query traverse --path project.stz --node api-gateway --field arch
statuz query impact --path project.stz --node auth-service
实现成本 低 — 每个命令是 load → engine API → save 的简单封装，clap derive 宏处理参数解析
用户体验 中 — 可脚本化、可组合、每次操作原子化；但构建复杂图时较繁琐
原型适配 最佳 — 最小改动实现"能存项目信息"的目标
长期价值 高 — CLI 命令是所有上层交互（REPL、Dashboard、MCP）的基础

选项 B：交互式 REPL

进入一个持续运行的交互式 Shell，在会话内维护 Cluster 状态，支持连续操作。

$ statuz shell --path project.stz
statuz> add-field arch "System Architecture"
statuz> add-node api-gateway --type service --label "API Gateway"
statuz> add-node auth-service --type service --label "Auth Service"
statuz> add-edge api-gateway -> auth-service --field arch --relation depends-on
statuz> query traverse api-gateway --field arch
  → auth-service (depends-on)
statuz> save
statuz> exit
实现成本 中 — 需要 REPL 循环、命令解析器、会话状态管理、错误恢复
用户体验 好 — 即时反馈、快速迭代、无需重复输入 --path
原型适配 良好 — 在 CLI CRUD 之上构建，是增强而非替代
长期价值 中 — 对开发者友好，但对非技术用户和 Agent 不如 CLI 命令直接

选项 C：文件驱动导入

用户在结构化文件（JSON 或 Markdown）中定义 Cluster 内容，通过 import 命令一次性导入。

// project-graph.json
{
  "name": "My Project",
  "fields": [
    {
      "id": "arch",
      "name": "System Architecture",
      "nodes": [
        { "id": "api-gateway", "type": "service", "label": "API Gateway" },
        { "id": "auth-service", "type": "service", "label": "Auth Service" }
      ],
      "edges": [
        { "from": "api-gateway", "to": "auth-service", "relation": "depends-on" }
      ]
    }
  ]
}

# 导入
statuz import --from project-graph.json --output project.stz
实现成本 低 — JSON 反序列化 + 引擎 API 调用，可复用 serde
用户体验 中 — 适合批量数据，不适合增量编辑；可版本控制
原型适配 良好 — 与 CLI CRUD 互补，解决"一次性导入大量数据"场景
长期价值 高 — 导入/导出是任何系统的必备能力，也为 arrow-map 提供输出目标

选项 D：Dashboard Web UI

基于 Web 的可视化界面，支持图形化创建节点、拖拽连线、力导向布局展示。

实现成本 高 — 需要前后端、图形渲染（D3.js/Cytoscape.js）、状态同步
用户体验 优秀 — 直观、可视化、最符合"Describe→Discover→Confirm"的理想
原型适配 不适合 — 设计文档定位为 Phase 6（50 天），远超原型范围
长期价值 高 — 人类管理 Statuz 的控制中枢

选项 E：自然语言 Describe→Discover→Confirm

用户用自然语言描述项目，arrow-map 翻译为 typed arrows，niche 做语义推断，用户确认后写入 Cluster。

实现成本 极高 — 需要 arrow-map + niche + syn 三个 crate 完整实现 + LLM 集成
用户体验 极致 — "Statuz understood my project" 的定义性体验
原型适配 不适合 — 三个 crate 目前是占位符
长期价值 最高 — 这是 Statuz 的核心竞争力和设计哲学终点

综合对比

选项 实现成本 用户体验 原型适配 长期价值 推荐阶段
A. CLI CRUD 低 中 最佳 高（基础设施） Phase 1
C. JSON 导入 低 中 良好 高（必备） Phase 2
B. 交互式 REPL 中 好 良好 中 Phase 3
D. Dashboard 高 优秀 不适合 高 Phase 4+
E. 自然语言 极高 极致 不适合 最高 远期愿景

五、原型范围定义

5.1 "能储存项目信息的原型"是什么

根据设计哲学文档和 AGENTS.md，"项目信息"在新范式里没有独立的一级概念——项目、组件、文件、人都是 Cluster 内的 Node，由 Edge 定义关系，由 Field 提供不同视角。"储存项目信息"等于把项目的实体与依赖关系建模为 Cluster 内的 nodes + edges + fields。

一个"能储存项目信息的原型"应满足以下用户故事：

  1. 创建：用户能创建一个空的 Cluster 并保存到文件
  2. 建模：用户能向 Cluster 添加字段（视角）、节点（实体）、边（关系）、桥接（跨字段连接）
  3. 查询：用户能对 Cluster 执行五大查询，获取拓扑关系信息
  4. 持久化：所有操作自动保存到 .stz 文件，下次可以加载继续
  5. 验证：用户能验证 Cluster 的结构一致性

5.2 原型不包含什么

  • Dashboard / Web UI（Phase 6）
  • 自然语言→图翻译（arrow-map，未实现）
  • 语义推断（niche，未实现）
  • 变更提案机制（syn，未实现）
  • 权重衰减、主动释放、注意力层（核心研究难题，存疑）
  • MCP 桥接（Phase 3）
  • 多 Agent 协调器（Phase 5）

5.3 成功标准

设计文档将北极星指标定义为"agent 跨 session 的上下文恢复成本"。但对于原型阶段，更务实的成功标准是：

"一个开发者能在 10 分钟内通过 CLI 创建一个包含 2 个字段、10 个节点、15 条边的 Cluster，保存为 .stz 文件，执行 traverse 查询获取依赖关系，并能在下次 session 中加载继续编辑。"

六、推荐方案

6.1 总体策略：CLI 先行，分阶段增强

推荐采用选项 A（CLI CRUD）作为 Phase 1，辅以选项 C（JSON 导入）作为 Phase 2，后续视需要增加选项 B（REPL）。理由如下：

  1. 引擎 API 已就绪——所有需要的操作（Cluster::new, register_node, create_field, add_bridge, traverse 等）在引擎层已实现并测试通过，CLI 命令只是薄封装
  2. CLI 是所有上层交互的基础——REPL 可以复用 CLI 命令解析器，Dashboard 后端可以复用 CLI 逻辑，MCP 工具可以包装 CLI 命令
  3. 最小改动实现最大价值——修复 init/save 链路 + 添加 CRUD 命令，预计 1-2 天即可让用户开始存储项目信息
  4. 与设计哲学一致——"Core 是底座，dashboard 才是盖摩天大楼的地方"，先把底座的交互通道打通

6.2 Phase 1：CLI CRUD 命令

修复现有命令断裂 + 添加核心 CRUD 和查询命令。

6.2.1 修复 init — 持久化到文件

# 当前（断裂）
statuz init --name "My Project"
# → 仅打印，不保存

# 修复后
statuz init --name "My Project" --output project.stz
# → 创建 Cluster + 生成 blake3 ID + 保存到 project.stz

修改要点：

  • init 接受 --output 参数，创建后立即序列化保存
  • 使用 generate_cluster_id()（blake3 内容寻址）替代 UUID
  • 可选：--visibility 和 --password 参数透传

6.2.2 修复 save — 保存指定 Cluster

# 当前（断裂）
statuz save --output project.stz
# → 总是保存 build_test_cluster() 演示数据

# 修复后：save 变为"重新序列化已有文件"或弃用
# 增量操作由 add-node/add-edge 等命令自动保存

修改要点：

  • save 不再调用 build_test_cluster()
  • 所有 mutation 命令（add-node, add-edge 等）在执行后自动保存
  • build_test_cluster() 保留用于 self-test，但不暴露给用户命令

6.2.3 新增 CRUD 命令

命令 引擎 API 参数
add-node cluster.register_node(node) --path, --id, --type, --label, --status
remove-node cluster.unregister_node(&id) --path, --id
add-field cluster.create_field(id, name, desc) --path, --id, --name, --description
remove-field cluster.remove_field(&id) --path, --id
add-edge field.graph.add_edge(edge) --path, --field, --from, --to, --relation, --weight, --description
remove-edge field.graph.remove_edge(&id) --path, --field, --id
add-bridge cluster.add_bridge(...) --path, --from-field, --to-field, --from-node, --to-node, --description

6.2.4 新增查询命令

命令 引擎 API 参数
query traverse cluster.traverse_across_fields(...) --path, --node, --field, --relation, --max-depth
query impact cluster.impact_across_fields(...) --path, --node
query path cluster.path_across_fields(...) --path, --from, --to
query subgraph cluster.subgraph(...) --path, --field, --seeds, --depth, --relation
validate cluster.validate() --path

6.2.5 完整用户流程

init → add-field → add-node → add-edge → query → show 
# 1. 创建 Cluster
statuz init --name "E-Commerce Platform" --output shop.stz

# 2. 添加字段（视角）
statuz add-field --path shop.stz --id arch --name "Architecture"
statuz add-field --path shop.stz --id data --name "Data Flow"

# 3. 添加节点（实体）
statuz add-node --path shop.stz --id api-gateway --type service --label "API Gateway"
statuz add-node --path shop.stz --id auth-service --type service --label "Auth Service"
statuz add-node --path shop.stz --id db-primary --type database --label "Primary DB"
statuz add-node --path shop.stz --id redis-cache --type cache --label "Redis Cache"

# 4. 在字段内添加边（关系）
statuz add-edge --path shop.stz --field arch \
  --from api-gateway --to auth-service --relation depends-on
statuz add-edge --path shop.stz --field arch \
  --from auth-service --to db-primary --relation depends-on
statuz add-edge --path shop.stz --field data \
  --from api-gateway --to redis-cache --relation produces

# 5. 添加跨字段桥接
statuz add-bridge --path shop.stz \
  --from-field arch --to-field data \
  --from-node api-gateway --to-node api-gateway \
  --description "Same service, different view"

# 6. 查询
statuz query traverse --path shop.stz --node api-gateway --field arch
statuz query impact --path shop.stz --node db-primary
statuz validate --path shop.stz

# 7. 查看
statuz show --path shop.stz

6.3 Phase 2：JSON 批量导入/导出

在 Phase 1 的基础上，增加 import 命令，支持从 JSON 文件批量导入 Cluster 内容。这使得用户可以用编辑器批量编写图结构，然后一次性导入。

  • statuz import --from graph.json --output shop.stz — 从 JSON 创建新 Cluster
  • statuz export --path shop.stz --output graph.json — 导出为 JSON（已有 export 命令，需确认格式对齐）
  • JSON schema 与 export_cluster_json() 的输出格式对齐

6.4 Phase 3：交互式 REPL（可选）

在 CLI CRUD 命令稳定后，可增加 statuz shell 交互模式。REPL 复用 Phase 1 的命令解析逻辑，在会话内维护加载的 Cluster 状态，避免每次操作都重复 --path 和文件 I/O。

6.5 与长期愿景的衔接

CLI CRUD (Phase 1) → JSON Import (Phase 2) → arrow-map (自然语言→JSON) → Describe→Discover→Confirm

CLI CRUD 是基础设施。当 arrow-map crate 实现后，它可以将自然语言描述翻译为 JSON，然后通过 import 命令导入——Phase 1 的 JSON 导入格式直接成为 arrow-map 的输出目标。这样，从手动 CLI 建模到自然语言建模的升级路径是平滑的，不需要推翻 Phase 1 的工作。

七、关键技术决策

7.1 状态管理：无状态 + 自动保存

每个 CLI 命令是无状态的——执行时加载 .stz 文件、修改 Cluster、保存回文件。这种方式有以下优势：

  • 原子性：每个命令成功后文件立即更新，失败则文件不变
  • 可组合：命令可以自由组合在 Shell 脚本中
  • 无状态丢失：不需要维护 session 文件或临时状态
  • 实现简单：不需要进程间通信或状态序列化

代价是每次操作都有文件 I/O（反序列化 + 序列化）。对于原型阶段的 Cluster 规模（几十到几百个节点），这个开销可以忽略。

7.2 ID 生成：统一使用 blake3 内容寻址

放弃 uuid::Uuid::new_v4()，统一使用 generate_cluster_id()（blake3 前 16 字节 hex 编码）。这符合设计哲学中"内容可寻址：相同内容产生相同 ID"的原则，也与存储格式中的 blake3 完整性哈希一致。

注意：blake3 内容寻址意味着 Cluster 内容变化后 ID 会变。这在当前阶段是可接受的——ID 用于标识 Cluster 的当前状态，而非永久身份。如果需要永久身份，可以在 meta 中存储一个 UUID 作为 stable identifier。

7.3 命令命名：动词-名词 + 子命令

遵循 statuz [动词]-[名词] [--参数] 的模式：

  • add-node, remove-node, add-field, remove-field, add-edge, remove-edge, add-bridge
  • query traverse, query impact, query path, query subgraph（query 作为子命令组）
  • 保留现有：init, show, save, load, verify, export, clone, merge, set-password, set-visibility, self-test

7.4 输出格式：结构化文本

查询结果以人类可读的结构化文本输出（缩进列表 + 关系标注），同时支持 --json 标志输出机器可读的 JSON。这兼顾人类阅读和脚本处理。

$ statuz query traverse --path shop.stz --node api-gateway --field arch

Traverse from: api-gateway (service: "API Gateway")
Field: arch

  api-gateway
    └──[depends-on]──▶ auth-service (service: "Auth Service")
                        └──[depends-on]──▶ db-primary (database: "Primary DB")

7.5 默认路径约定

支持在工作目录下查找 .statuz 配置文件或默认的 statuz.stz 文件，减少 --path 的重复输入。如果当前目录存在 statuz.stz，则自动使用；否则要求显式指定 --path。
