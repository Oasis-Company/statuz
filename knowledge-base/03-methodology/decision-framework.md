# 决策框架

> 设计决策的方法论和原则

---

## 一、核心决策框架

### 1.1 范式转换原则

当遇到"这个系统应该是什么"的问题时，使用以下框架：

```
1. 最小可行单位是什么？
   → 不是"协议"，而是"引擎"
   → 不是"文档系统"，而是"图容器"

2. 用户最常进行的操作是什么？
   → 不是"读写 YAML 文件"，而是"查询节点关系"

3. 什么是不变的？
   → 节点和边的关系（拓扑结构）
   → 内容可寻址
   → 离线工作

4. 什么是可变的？
   → 存储格式（YAML → msgpack）
   → 语言（TypeScript → Rust）
   → 协议层（分离出去）
```

### 1.2 决策优先级

1. **用户价值**：这个决策最终对用户有什么影响？
2. **工程简洁**：这个决策是否降低了系统复杂度？
3. **可验证性**：这个决策的结果能否被测试验证？
4. **可逆性**：如果这个决策错了，能轻松回滚吗？

### 1.3 反模式识别

- **"通用化陷阱"**：为一个可能永远不会出现的场景做通用设计
  - 避免：在 Phase 1 就设计插件系统
  - 应该：先解决具体问题，再抽象

- **"协议化陷阱"**：把工具做成协议
  - 避免：Statuz 定义传输协议
  - 应该：Statuz 是引擎，MCP 是传输

- **"文档化陷阱"**：用文档代替代码
  - 避免：100+ 个 `.md` 文件，但代码没有实现
  - 应该：代码即文档，注释补充解释

## 二、存储范式决策

### 2.1 为什么是 msgpack 而不是 YAML？

| 维度 | YAML | msgpack |
|------|------|---------|
| 人类可读 | 是 | 否 |
| 解析速度 | 慢 | 快 |
| 二进制安全 | 否 | 是 |
| 大小 | 大 | 小 |
| 内容寻址友好 | 否（空行/注释影响哈希） | 是（确定性序列化） |

**决策**：msgpack，因为引擎是内部工具，不需要人类直接编辑 .stz 文件。

### 2.2 为什么是 Cluster 而不是 Arrow Map？

Arrow Map 描述的是"关系"，Cluster 描述的是"容器"。

- Arrow Map 是声明式：你声明节点和箭头的存在
- Cluster 是命令式：你构建图、查询图、存储图

**决策**：Cluster，因为引擎需要可编程实体，而不是声明式文件。

### 2.3 为什么是 BFS 而不是 Dijkstra？

- 图是无权重的（所有边权重为 1）
- 不需要考虑路径成本
- BFS 保证无权图的最短路径

**决策**：BFS，因为足够的简洁性 + 正确性。

## 三、技术栈决策

### 3.1 Rust 决策树

```
为什么不是 TypeScript？
├── 图算法性能：TS 在 O(n) 遍历中有 GC 暂停
├── 零 GC：Rust 的所有权模型保证确定性内存管理
└── 内容可寻址对齐：blake3 哈希、二进制序列化、Rust 的严格类型

为什么不是 Go？
├── Go 的 goroutine 在这里没有用（单线程图操作）
└── Rust 的枚举系统更适合图类型（NodeType、Relation 枚举）

为什么不是 C++？
├── C++ 没有包管理器等效于 Cargo
└── Rust 的所有权检查器在编译时防止内存错误
```

### 3.2 官网技术栈决策

```
为什么不是 React？
├── 官网的核心内容是文本 + 图 + 代码块
├── 不需要组件化
├── 零框架意味着零构建步骤
└── 直接 git push 到 GitHub Pages
```

### 3.3 依赖决策

| 原则 | 说明 |
|------|------|
| 零非 serde 依赖 | 图算法使用 std 集合 |
| 最小依赖 | 只添加必要的 crate |
| 锁定版本 | Cargo.lock 提交到仓库 |
