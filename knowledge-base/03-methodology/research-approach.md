# 研究方法

> 研发过程中使用的信息收集和分析方法论

---

## 一、信息收集策略

### 1.1 搜索优先级

1. **代码库优先**：先在 `crates/`、`packages/`、`docs/` 中搜索
2. **记忆优先**：检查 `memory/` 中的项目记忆和用户偏好
3. **Web 搜索**：代码库和记忆不足时，使用 WebSearch
4. **权威源优先**：官方文档 > 技术博客 > 社区讨论

### 1.2 搜索模式

| 场景 | 搜索方法 | 工具 |
|------|---------|------|
| 找文件 | 按文件名模式匹配 | Glob |
| 找代码 | 按正则表达式搜索内容 | Grep |
| 找定义 | 搜索类/函数/类型定义 | Grep + 文件模式 |
| 找外部信息 | 最新版本、API 文档、最佳实践 | WebSearch |
| 探索代码库 | 打开多个相关文件 | Task(Explore) |

### 1.3 信息消化方法

- **先读小文件**：`AGENTS.md` > 模块入口 > 类型定义 > 实现
- **先读数据结构**：理解类型定义后再读算法
- **先读测试**：测试用例是最好的文档

## 二、技术研究方法

### 2.1 Rust 技术研究

- **官方文档**：`doc.rust-lang.org` 优先
- **crate 文档**：`docs.rs` 查看 crate API 文档
- **源码阅读**：当文档不足时，直接读 crate 源码
- **最小复现**：在临时文件中写最小示例验证理解

### 2.2 设计研究

- **竞品分析**：对比同类工具的设计决策
- **模式匹配**：从已知的成功模式中提取可复用的部分
- **第一性原理**：从核心约束出发推导设计，而不是照搬现有方案

### 2.3 前端设计研究

- **灵感来源**：Landingfolio、SaaS Landing Page 等设计灵感网站
- **竞品拆解**：分析 Bevy、Tokio、Axum 等 Rust 项目官网的设计语言
- **差异化策略**：避免"AI 生成的通用设计"（紫色渐变、Space Grotesk、Inter 字体）

## 三、范式转换方法论

### 3.1 识别范式错误的信号

1. **文档与代码脱节**：100+ 个 `.md` 文件，但代码没有实现
2. **复杂度不可控**：添加新功能需要修改 5+ 个文件
3. **测试覆盖率下降**：新功能没有对应的测试
4. **"本该如此"的直觉**：如果感觉"这个设计不对劲"，那很可能确实不对劲

### 3.2 范式转换触发条件

```
问自己三个问题：
1. 如果从头开始，我会怎么设计？
2. 当前设计的哪些部分让我感到"沉重"？
3. 用户真正需要的东西是什么？
```

### 3.3 范式转换后的处理

- 旧代码不删除，标记为"冻结"
- 旧文档不删除，归档到 `leftover/`
- 旧规则不沿用，记录到 `project_memory.md` 作为教训

## 四、学习策略

### 4.1 从旧系统学习

- 旧 TypeScript 系统的教训记录在 `01-achievements/legacy-achievements.md`
- 核心教训：文档与代码不能脱节，类型安全不能妥协

### 4.2 从失败中学习

- 范式转换的根本原因：将"协议"和"引擎"混为一谈
- 解决方案：将协议层分离（MCP），专注于引擎核心

### 4.3 从成功中学习

- Rust 引擎成功的三个因素：
  1. 明确的核心（图引擎 + 三个查询）
  2. 严格的约束（零非 serde 依赖、内存优先）
  3. 可验证的交付物（self-test + 10 Phase）
