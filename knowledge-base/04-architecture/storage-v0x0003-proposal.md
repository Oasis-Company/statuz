## 二、需求推导：AI 需要什么信息、怎么访问

### 2.1 信息清单

| 信息 | 性质 | 衰减性 | 来源 |
|------|------|--------|------|
| 拓扑事实（节点/边/关系/权重） | 结构 | 永不衰减 | IDEA.md："Structure is fact. It never decays." |
| 注意力状态（什么刚变、此刻什么重要） | 派生 | 会衰减 | IDEA.md / HARD-TODO #1 |
| 内容（label/描述/meta） | 负载 | 弱衰减 | types.rs |
| 变更历史（diff、审计、观察流） | 时间线 | 衰减 | Loop / syn 协议 |
| 语义解释（漂移、解读） | 派生 | 会衰减 | niche（占位） |

### 2.2 访问模式 → 物理含义

| 场景 | 访问模式 | 物理含义 |
|------|---------|---------|
| 会话启动注入（北极星） | seed → BFS 子图 + top-k 注意力 | 只读文件一小部分 → **区段化 + 惰性解码**；注意力索引廉价物化 |
| 运行时查询 | traverse/impact/path 随机点查 | **邻接按源节点连续存放**（顺序读） |
| agent 回写 | 小增量 diff → merge | 写放大 → **快照为主 + delta/WAL 为辅**（双时钟） |
| 共享 | 文件复制、内容寻址、加密 | 不可变容器 + 外部稳定 ID |
| 记忆引擎 | 追加观察流 + 按种子召回 + 衰减评分 | **时间维度**：事件日志 + recency 索引 + 热/冷分层 |
| 多 agent 并发 | 共享读、隔离写 | 单文件不可变快照天然适配 |

### 2.3 存储边界（生态位的物理化）

- **Statuz 存**：结构 + 状态 + 时间（拓扑、注意力、变更历史）
- **Statuz 不存**：内容本体（留在文件系统）、嵌入/向量（向量库的活，存相似性丢拓扑）、对话 transcript（宿主的活）
- 理由：记忆引擎领域（MemGPT/Letta 分层记忆、Mem0 抽取式记忆）的教训——内容记忆与结构记忆是两回事；Statuz 只对结构负责，内容用指针引用

## 三、物理设计空间（业界方案取舍）

| 维度 | 方案 | 结论 |
|------|------|------|
| 记录布局 | 全对象 blob（现状，350B/边）/ 定长记录+free-list（Neo4j）/ **列式分区** | 列式分区（节点区/边区/属性区分离） |

| 压缩 | 字典（interning）/ delta 编码 / 位打包 / zstd | 字典为地基，zstd 保持 |

## 四、v0x0003 容器轮廓

```
.stz 容器（内容寻址，不可变快照）
├── header        magic/version/flags/分区偏移表
├── string table  id 与属性值字典（interning，压缩地基）
├── node section  紧凑记录：u32 内部 id ↔ 外部 id、type、status、属性偏移
├── edge section  CSR 出边 + CSC 入边（平行数组，含桥边标记）
├── attention     recency 时间戳、度数、centrality top-k 缓存（D1' 索引的持久化形态）
├── [delta 段]    可选：追加式变更日志（方向 C 的落点）
└── trailer       blake3（只覆盖逻辑内容，不覆盖内部布局）
```

**与北极星的对齐**（设计验收标准）：
- 注入 = header + attention + 种子边区段 → 一次 BFS → top-k：全程顺序读，不解码全图
- impact = in-CSR 顺序读（D1' 内存索引的磁盘同构）
- 回写 = diff → delta 段或新快照（内容寻址天然版本化）
- 记忆引擎 = 观察流进 delta 段 + recency 物化进 attention 段；遗忘/折叠 = 冷区归档（方向 E）

## 五、第一决策：内部数值 id 空间（研究定义）

### 5.1 为什么是它

D1' 硬数据：String id 是全部剩余瓶颈的根（SipHash ~100ns/次 × BFS 每次访问 3-5 次；100k 边 350B/边的开销大半是 String）。方向 A（磁盘格式）和方向 B（BFS 物理化）都建立在数值 id 之上——没有它，两者都是空中楼阁。

### 5.2 设计要点

- **外部 id**：内容寻址 blake3（永不衰减，供共享/引用/比较）
- **内部 id**：u32（插入序或字典序），仅在内存与磁盘布局内使用
- **映射层**：`HashMap<外部String, u32>` + 反向 `Vec<外部String>`（字典），随加载构建、随写入维护
- **内容寻址的语义**：blake3 哈希"逻辑内容"（节点/边集合的规范化表示），不哈希物理布局——内部 id 随插入漂移，但"相同内容相同 ID"（ADR 硬规则）必须保持

### 5.3 原型研究（验证什么）

1. **收益验证**：GraphEngine 内部 BFS 换 u32 + Vec 邻接（原型级），测量 impact/traverse 在 100k/1M 边的 µs/op——对照 D1' 的 90µs（BFS 地板）与 10.4ms（跨域全图）
2. **映射层成本**：加载时构建映射（String→u32）的时间/内存——对照 T4 预算
3. **字典压缩率**：真实图（D2' 素材：statuz 自举图）的 id 字典压缩效果
4. **注入路径原型**：header + attention + 边区段的顺序读耗时——对照 ≤100ms 预算

### 5.4 验收标准

- 100k impact(local) 从 90.4µs → 目标 ≤20µs（u32 BFS + bitset visited）
- 100k impact(cross) 从 10.4ms → 目标 ≤1ms（若数值 id 全链路化）
- 映射构建 ≤50ms @100k、≤500ms @1M
- 正确性：与 String 实现的属性对照 100/100（沿用 D1' 测试模式）
- 磁盘格式不变（原型阶段仍是 serde-skip 派生物，v0x0003 才落盘）

## 六、注入 ≤100ms：预算分解（研究期测量项）

| 段 | 预算 | 说明 |
|----|------|------|
| 文件打开 + header | ≤1ms | 固定偏移读取 |
| 映射/字典加载 | ≤20ms @100k | string table 顺序读 |
| attention 段（recency/度数） | ≤5ms | 定宽记录顺序读 |
| 种子边区段 | ≤50ms @100k | CSR 顺序读 + BFS |
| top-k 选择与格式化输出 | ≤10ms | select_top_k 现有实现 |
| 余量 | ~15ms | 系统噪声 |

预算分解为研究期测量项，D2' 真实图报告 + 数值 id 原型共同校准。

## 八、开放研究问题

1. **内容寻址 vs 内部 id**：blake3 哈希逻辑内容（规范化表示）——规范化成本？边集合的规范化排序在 1M 边时耗时多少？
2. **注入延迟实测**：D2' 真实图上测量各段的真实耗时，校准 §六 预算
3. **边记录宽度**：u32 内部 id 支持 42 亿节点——够；属性字典的粒度（全局 vs 分区）影响压缩率
4. **delta 段 vs 快照临界点**：双时钟判断——多少小写之后值得重写快照
5. **社区分块**（HARD-TODO #4 packfile 思想）：边按社区聚簇能否提高注入局部性——D2' 真实图验证
6. **记忆引擎的衰减物理表达**：recency 每节点时间戳（简单）vs 观察事件流（精确）——决定 attention 段形态
