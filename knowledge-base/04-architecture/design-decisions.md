# 设计决策记录

> Architecture Decision Records (ADR) 的轻量版本
> 记录每个重要决策的上下文、选项和选择理由

## 一、范式级决策

### ADR 001：Rust 替代 TypeScript

**上下文**：2026-07-11，发现 TypeScript 版本存在文档与代码严重脱节（100+ 个 `.md` 文件，但代码没有 Cluster 容器），且图算法性能不足。

**选项**：
1. 继续 TypeScript，修复文档与代码的脱节
2. 切换到 Rust，从头构建图引擎
3. 混合方案：TypeScript CLI + Rust 核心引擎

**决策**：选项 2（Rust 替代 TypeScript）

**理由**：
- 图算法性能：Rust 的零 GC 和确定性的内存管理
- 内容可寻址对齐：blake3 哈希、二进制序列化、Rust 的严格类型系统
- 不可逆的范式的转换：从"协议"到"引擎"的认知转变需要完全重写

**代价**：所有旧代码（TypeScript SDK、CLI、MCP Server、VS Code Extension）被冻结，等待 Rust 版本取代。

---

### ADR 002：Cluster 取代 Arrow Map / niche / SYN

**上下文**：旧系统有 4 种文件格式（Arrow Map、niche、SYN、Core），每种有自己的 JSON Schema 和 YAML 文件。

**选项**：
1. 保留多种文件格式，统一在 Rust 中实现
2. 合并为一种存储单元（Cluster）

**决策**：选项 2（Cluster 作为唯一存储单元）

**理由**：
- 单一容器简化了存储、序列化、共享和验证
- Cluster 自包含：所有节点、边、元数据在一个文件中
- 内容可寻址：相同内容产生相同 ID

---

### ADR 003：三项查询是引擎的全部 API

**上下文**：在定义引擎 API 时，需要考虑应该暴露多少查询能力。

**选项**：
1. 通用图查询（类似 Cypher 或 SPARQL）
2. 三项精确查询（traverse / impact / path）
3. 只有基本遍历，查询由上层实现

**决策**：选项 2（三项查询）

**理由**：
- 三项查询对应三个认知操作：探索（traverse）、风险评估（impact）、路径规划（path）
- 覆盖 95% 以上的实际使用场景
- 足够简单，可以保证正确性和性能

## 二、架构级决策

### ADR 004：Field 子图 + Bridge 桥接

**上下文**：如何在 Cluster 中组织多个视角（如架构视图、数据流视图、团队视图）。

**选项**：
1. 所有节点和边在一个图上，用标签过滤
2. 每个视角一个独立的图，通过桥接连接

**决策**：选项 2（Field + Bridge）

**理由**：
- 视角隔离：不同团队看到不同的子图
- 跨域通信：通过 Bridge 边实现跨 Field 遍历
- 路径追踪：`PathResult.field_path` 记录经过的字段

---

### ADR 005：离线共享（Clone + Merge），不涉及网络

**上下文**：Cluster 如何在不同用户之间共享。

**选项**：
1. 网络同步（类似 Git 的 push/pull）
2. 离线文件共享（复制 .stz 文件）
3. 混合方案

**决策**：选项 2（离线文件共享）

**理由**：
- 简单：不需要网络协议、服务器、认证
- 安全：密码保护 + 加密，文件传输完全在用户控制下
- 合并策略：4 种策略（Skip / Overwrite / Rename / MergeMeta）覆盖所有冲突场景

---

### ADR 006：内存优先，序列化是快照

**上下文**：图操作和序列化的关系。

**选项**：
1. 数据库风格：每次操作后自动持久化
2. 内存优先：所有操作在内存中，显式调用 save 才持久化

**决策**：选项 2（内存优先）

**理由**：
- 性能：内存操作远快于磁盘操作
- 简单：不需要事务日志、WAL 等复杂机制
- 用户控制：用户决定何时保存

## 三、技术级决策

### ADR 007：msgpack 而非 YAML

**上下文**：存储格式的序列化协议选择。

**决策**：msgpack

**理由**：
- 确定性序列化：相同数据产生相同字节，YAML 受空行、注释影响
- 二进制安全：支持加密后的二进制数据
- 大小：比 YAML 小 3-5 倍
- 解析速度：比 YAML 快 10-100 倍

---

### ADR 008：BFS 而非 Dijkstra

**上下文**：path 查询的算法选择。

**决策**：BFS

**理由**：
- 所有边权重为 1（无权图），BFS 保证最短路径
- 不需要考虑路径成本
- 实现简单，性能好

---

### ADR 009：零非 serde 依赖

**上下文**：Rust 依赖策略。

**决策**：图算法使用 std 集合，不引入第三方图库

**理由**：
- 减少依赖风险
- 完全控制实现细节
- 代码量小（~180 行），不需要第三方库

---

### ADR 010：clap 而非手动解析 CLI

**上下文**：CLI 参数解析库选择。

**决策**：clap（derive 模式）

**理由**：
- 自动生成 --help 和 --version
- 类型安全的参数解析
- 支持子命令嵌套

---

## 四、官网级决策

### ADR 011：单页 HTML 而非框架

**上下文**：官网技术栈选择。

**决策**：单页 HTML + 内联 CSS + 内联 JS

**理由**：
- 零构建步骤，直接 git push 到 GitHub Pages
- 零依赖，加载时无外部请求失败风险
- 核心内容是文本 + 图 + 代码块，不需要 React 组件化

---

### ADR 012：Architectural Blueprint 而非典型 SaaS 设计

**上下文**：官网视觉设计方向。

**决策**：Architectural Blueprint（架构蓝图）

**理由**：
- 与产品（图引擎）一致
- 与 Logo（三条线 + 一个圆点）一致
- 差异化：避免"AI 生成的通用设计"（紫色渐变、Inter 字体）

---

### ADR 013：SVG 内联而非图片

**上下文**：官网中所有图（节点图、架构图、概念图）的渲染方式。

**决策**：所有 SVG 内联，使用 CSS 变量

**理由**：
- 支持深色/浅色模式自动适配
- 零外部请求
- 可维护性：修改 SVG 不需要重新生成图片文件
