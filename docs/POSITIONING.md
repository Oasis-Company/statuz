# Statuz 战略定位

> 我们不竞争 token 数量，我们竞争每个 token 的信息密度。

## 两条路

AI 行业在为 Agent 提供上下文这件事上，有两条路可以走：

| | Industry Road | Statuz Road |
|---|---|---|
| **方向** | 更多容量 | 更多相关性 |
| **比喻** | 把仓库造得更大 | 给仓库装 GPS |
| **核心指标** | 上下文窗口大小 (tokens) | 信息密度 (meaningful bits / token) |
| **瓶颈** | 硬件成本 · 注意力机制平方复杂度 | 图算法 · 拓扑结构设计 |
| **谁在做** | Google, OpenAI, Anthropic | 只有我们 |
| **关键问题** | 「能不能装下」 | 「该装什么」 |

## 为什么不是竞争关系

Big context 和 Statuz 解决的是**正交问题**：

```
Big Context（行业方向）:
  "给你 2M tokens，你自己在里面找"
  → 容量优势，但相关性要靠 agent 自己搜索
  → 问题：haystack 越大，needle 越难找

Statuz（我们的方向）:
  "在你给定的 token 预算里，这是最相关的子图"
  → 容量不限，每一次释放都是精准的
  → 优势：即使 token 预算不变，信息有质变
```

两者同时使用，才构成完整的 Agent 上下文方案：
```
Big Context + Statuz = 既有空间装下一切，又有方向知道先看什么
```

## 历史类比：搜索引擎

1998 年之前：雅虎等门户竞争「收录更多网页」（越大越好）

1998 年 Google：不竞争收录量，竞争**相关性**（PageRank 决定哪些页面值得看）

Statuz 对上下文做的事 = PageRank 对网页做的事：

> 不是给你更多，而是告诉你什么更值得看。

## 为什么大厂不会轻易做这个

1. **做大上下文是硬件问题**（加内存、优化注意力），工程可解
2. **做信息密度是理论问题**（图压缩、主动释放），需要研究突破
3. 大厂的激励结构偏向「更大的数字」—— 更好宣传
4. 信息密度的突破很难量化、很难宣传、很难成为 PR 亮点

## 这个定位意味着什么

1. **不需要等 LLM 支持 10M token 上下文** —— 我们现在就可以开始
2. **Statuz 对任何 token 预算都有效** —— 100K 也好，1M 也好，价值不变
3. **如果未来上下文窗口近乎无限，Statuz 仍然有用** —— 因为即使有无限空间，agent 也需要知道先关注什么
4. **我们的护城河不是代码，是方向** —— 大厂很难转身来走这条路

## 一句话定位

> **Big context makes the pipeline bigger. Statuz makes what flows through it worth reading.**
