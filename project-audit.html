Statuz 项目严苛评估报告

使命与现实之间的鸿沟
2026-07-14 | 基于代码库深度审查、文档分析和架构评估

当前状态：不可达到所宣称的使命

Statuz 的核心使命——"让 AI 主动知道状态，实现真正的人机协同"——在当前代码库、时间线和团队条件下不可实现。项目宣称的愿景与实际情况之间存在巨大的鸿沟，其中 80% 的核心功能尚未开始研究，而已经完成的部分仅停留在概念验证级别。

二、使命拆解与现实对照

致命 使命核心 #1：信息主动释放（工作记忆）
哲学 代码
哲学宣称："信息不是被动检索，而是主动释放，就像人脑的工作记忆，让 agent 真正知道该干什么。"
现实状态：Engine 仅有被动查询 API（traverse、impact、path）。没有任何主动推送机制。HARD-TODO.md 将此列为 P0 难题，难度 4/5，预估 3-6 个月研究 + 1-2 个月原型，状态为❌ 未开始。
结论：这是整个项目存在的根本理由。没有它，Statuz 只是一个功能有限的图存储库，完全无法实现其宣称的"人机协同"愿景。
致命 使命核心 #2：Better Loop
哲学 代码
哲学宣称："Better Loop" 是三大支柱之一。STATUS → DETECT → UPDATE → STATUS 循环。
现实状态：Engine 有 diff() 方法，但没有任何循环机制、收敛条件、事件到图映射规则。HARD-TODO.md 列为 P0 难题，难度 4/5，状态为❌ 未定义。不同 node type 的循环频率如何分级？中断和恢复机制是什么？完全没有答案。
致命 使命核心 #3：语义理解与拓扑分析
哲学 代码
哲学宣称："利用拓扑结构、语义学和循环模式，做到真正的人机协同。"
现实状态：语义引擎（niche crate）是6 行代码的占位符。语义压缩列为 P1 难度 5/5，预估 6-12 个月研究 + 3-6 个月原型，标注"需要图论教授参与"。拓扑分析仅停留在最基本的 degree centrality 和 BFS 层面——这是图论入门课程的内容，远非"超一流图结构"。
严重 支撑能力：代码到图的自动构建
代码
宣称：图应自动从真实代码构建（读 package.json、AST、git log）。
现实状态：所有测试图中的节点和边都是手工编码的。旧 detect --auto 是 stub 实现（已归档）。HARD-TODO.md 列为 P1 难度 3/5，❌ 未开始。没有这个能力，Statuz 无法在任何真实项目上运行，所有演示都是手造的。
严重 支撑能力：原生图存储格式
代码
宣称：需要一种以 edge 为中心的轻量存储格式，按社区分块，支持实时性。
现实状态：当前存储格式是简单的二进制序列化（msgpack + blake3）。没有 WAL、没有社区分块、没有 edge-first 存储。HARD-TODO.md 列为 P1 难度 5/5，❌ 未开始，预估 12-18 个月，标注"需要存储系统专家"。
严重 支撑能力：Better Diagram
哲学 代码
宣称：三大支柱之一。
现实状态：Dashboard 是静态 HTML 页面，与引擎零连接。无法可视化任何实际图数据。没有交互式图查看器，没有拓扑可视化，没有实时状态展示。Dashboard 目前只是一个营销页面，而不是工具界面。
中等 自举测试
哲学
宣称：Statuz 必须能吃自己的狗粮——运行在 Statuz 项目自身上。
现实状态：HARD-TODO.md 列为 P2 难度 3/5，❌ 未开始。如果 Statuz 连自己都理解不了，它就理解不了任何复杂项目。这是一个反射测试，也是项目可信度的关键指标。

四、代码质量：表面光鲜，暗藏隐患

4.1 编译阻断性 Bug

严重级别：致命
main.rs:125 使用 uuid::Uuid::new_v4()，但 Cargo.toml 中未声明 uuid 依赖，Cargo.lock 中也无 uuid 的任何记录。编译直接报错。
这是最基础的工程错误——添加依赖后忘记在 Cargo.toml 中声明。项目宣称的"July MVP"连编译都做不到。

4.2 AGENTS.md 硬规则违反

规则违反情况严重程度
库代码中无 unwrap() graph/engine.rs 2 处、cluster/cluster.rs ~10 处、storage/mod.rs 4 处，共约 16 处 unwrap() 严重
无死代码 AdjacencyCell.node_id 字段从未使用；standalone_test.rs 650 行孤立文件 中等
无深度嵌套 run_self_test() 363 行单函数，远超 200-400 行惯例 轻微

4.3 确凿 Bug

remove_node() 不清理反向引用
删除节点 A 后，依赖于 A 的节点 B 的 incoming 邻接表中仍保留指向已删除边的引用。在特定操作序列下会导致状态不一致。
blast_radius 字段行为不一致
GraphEngine::impact() 将 blast_radius 设为空向量，但 Cluster::impact_across_fields() 将 blast_radius 设为与 affected 相同。同一概念的两种实现，语义不一致。
create_field() 返回 &mut Field——Rust 借用检查器陷阱
返回对内部 HashMap 的可变引用是 Rust 中的已知反模式。当前代码虽能编译，但任何在返回后对 Cluster 的 &mut 借用都会破坏此模式。

4.4 测试覆盖：报告中的亮点

测试覆盖值得肯定（约 103 个 #[test] 函数）
graph/query.rs 有 30 个测试、cluster/cluster.rs 有 29 个测试、storage/mod.rs 有 14 个测试，覆盖了边界情况和错误路径。这是项目中质量最高的部分。

4.5 代码重复与结构问题

  • build_test_cluster() 三重重复：分别存在于 main.rs（约 176 行）、cluster/cluster.rs 测试模块、standalone_test.rs 中。违反 DRY 原则。
  • standalone_test.rs 650 行孤立文件：未被任何模块引用，无法编译（与 main.rs 的 fn main() 冲突）。属于死代码。
  • 占位符 crate 膨胀：arrow-map、niche、syn、statuz-core-napi 四个 crate 各只有 6 行有效代码，但作为工作区成员参与编译。

七、两条路径

路径 A：诚实定位
接受 PoC 状态，缩减愿景
  • 将项目定位为"Rust 图存储引擎 + 查询库"，而非"人机协同平台"
  • 修复编译错误，消除库代码 unwrap，解决 remove_node 反向引用 bug
  • 删除 standalone_test.rs 死代码，消除 build_test_cluster 三重重复
  • 更新官网，诚实标注 PoC 状态，移除虚假链接
  • 将 HARD-TODO.md 难题转化为长期研究路线图（3-5 年）
  • 重写哲学文档，使用专业语言，添加版本号和量化里程碑
可行性：高。1-2 周内可完成。结果是诚实、可用的基础工具。
路径 B：坚持使命
承认这是长期研究项目
  • 明确放弃"七月 MVP"截止日期
  • 将研究路径文档化为 RFC 或白皮书（图工作记忆、Loop 数学定义、语义压缩）
  • 寻找学术合作者（图论、存储系统领域）
  • 建立可量化的成功指标和阶段性验证
  • 在 GitHub 上作为研究项目开源，而非产品
  • 考虑在学术会议（如 VLDB、SIGMOD）上发表论文验证核心思路
可行性：低。需要外部学术资源，结果不可预测。但这是实现"人机协同"愿景的唯一路径。

八、最终结论

Statuz 当前无法达到其宣称的使命

核心原因不是代码不够好——代码质量在测试覆盖方面甚至值得肯定——而是哲学与代码之间的鸿沟远远大于任何短期工程努力可以填补的。项目所宣称的"主动释放"、"图 Loop"、"语义理解"是研究级难题，而非工程级难题。将它们包装成可以在一个"七月"内完成的产品，要么是严重误判，要么是刻意夸大。

HARD-TODO.md 的最后一句是整个项目中最诚实的声明：

"当前 Engine 和 Dashboard 是概念验证级（PoC）。从 PoC 到产品，差距在研究 1-7 全部完成。"

如果 Statuz 的目标是成为一个"功能有限的 Rust 图存储引擎"，它已经走在正确的道路上。但如果使命是"让 AI 真正知道自己在干什么"，那么当前状态距离这个目标还有 3-5 年的研究差距，且需要外部学术资源支持。
