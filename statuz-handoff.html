Statuz 项目交接文档

为 AI Agent 设计的持久化依赖图引擎 — Better Engine, Better Diagram, Better Loop

日期: 2026-08-02 语言: Rust 状态: Phase 4 引擎完善中 代码量: ~2500 行 Rust

项目概述

Statuz 是一个持久化、跨工具的依赖图引擎，为 AI Agent 设计，配有决定 Agent 当前需要知道什么的注意力层。它不是协议、不是数据库、不是 RAG 系统——它是 agent 状态基础设施，更接近文件系统或版本控制对象模型。

权威定位文档：POSITIONING_7_25.md（2026-07-25）。当其他文档与此冲突时，以此为准。

核心问题

LLM 始终在预测和压缩，信息留存量递减，文档完全无用。用户不可能任何时间都进入良好的工作状态，几个提示词下去整个对话节奏就全乱了。Statuz 要解决的核心问题是：让 AI 知道自己和项目的状态——知道自己在干什么、意义何在、在整体生态位中的位置。

什么不是 Statuz

不是原因
传输协议那是 MCP 的职责。Statuz 通过 MCP 被访问，不替代它
数据库没有超过三个查询以外的操作
向量存储 / RAGRAG 假设 Agent 知道该问什么，长周期 Agent 不知道
内容数据库不存储源文件/文档，只存储拓扑关系
YAML 文档系统旧范式已死，引擎使用 msgpack 二进制存储
实时同步系统仅离线文件共享

北极星指标

Context-recovery cost：Agent 在会话边界后，达到能有效处理长周期任务状态所需的工具调用数（或 token 数）。通过 judge statuz 配对 A/B 测试衡量。

设计哲学

来源：STATUZ设计哲学的论述.md — Dr. Ceaserzhao

Better Engine

depsgraph 同构的内核。纯拓扑计算，无语义判断。Cluster 原始图是权威的、内容寻址的。

Better Diagram

工作集投影。Agent 和人类实际看到的是注意力排名的评估图，而非原图。

Better Loop

tag → impact-flush → recompute attention。增量、多速率循环。结构变更和价值变更走两个时钟。

核心设计原则

  • 信息主动释放：像人脑工作记忆，而非被动检索。这是与 RAG 的根本区别
  • 不被上下文局限：项目和生态系统的全部关键信息保存在 Statuz 里，让 Agent 无缝打工
  • 功能涌现：Statuz 只专注核心和交互模式，功能从基座中涌现
  • 双图分离：Cluster 原始图永不被评估修改，排名/衰减/上下文化存在于派生的工作集投影中
  • impact() 是传播原语：不仅是读查询，事件标记变更节点后沿依赖边刷新

主动释放的管道定义

主动释放不是任何一层能单独声称的组件，而是一个端到端管道：

  1. 内核发射纯拓扑信号（中心性、新近性、差异量级、种子随机游走分数）
  2. 表征层为特定 (agent, task) 执行相关性仲裁
  3. 结果是 Agent 接收的工作集投影

Cluster 生态系统

Cluster 是信息宇宙的边界——共享本体论成立的最大单元。两个 Cluster 之间不能联通（设计约束，非技术限制）。

图 4: Cluster 生态 — 多 Field + Bridge + Cluster 边界 + 未来愿景

Cluster 边界论述

  • Cluster 边界是逻辑后果，不是待修复的缺陷
  • 传输问题已解决（MCP 的职责）；对齐问题是开放的（数十年未解难题）
  • 跨 Cluster 桥接只能在表征层生成置信度加权的假设映射，永不进入内核作为边
  • "我们自己的 A2A 模式" = 表征层生成置信度加权、始终可修订的 Cluster 间假设映射

未来愿景

Cluster 将像 GitHub 仓库一样运作——每个公司或个人拥有多个 Cluster，作为云端组件。公司主 Cluster 包含不同 Field（架构、数据流等），个人 Cluster 包含研究 Field。

GraphEngine 核心数据结构

pub struct GraphEngine {
    nodes: HashMap<NodeId, Node>,
    edges: HashMap<EdgeId, Edge>,
    adj: HashMap<NodeId, AdjacencyCell>,
}

pub struct AdjacencyCell {
    pub outgoing: HashMap<String, Vec<Edge>>,  // relation → 出边
    pub incoming: HashMap<String, Vec<Edge>>,  // relation → 入边
}

邻接表按 relation 分组存储，支持按关系类型 O(1) 过滤查询。边数据克隆两份分别存入 source 的 outgoing 和 target 的 incoming，实现双向查找。

存储格式

.stz 二进制格式：msgpack + blake3 + argon2 + zstd + chacha20。

图 8: 存储格式 — 二进制布局 + 序列化/反序列化流程 + 加密细节

二进制布局

[magic: 4B]     "STZ\0" (0x53 0x54 0x5A 0x00)
[version: 2B]   u16 LE (当前 0x0002, 兼容 0x0001)
[flags: 2B]     bit0=encrypted, bit1=compressed
[salt: 16B]     argon2 salt (v0x0002+, 未加密时全零)
[content: 变长] msgpack 编码的 Cluster (可选压缩+加密)
[hash: 32B]     blake3 完整性哈希 (仅覆盖 content)

加密细节

  • 密钥派生：argon2id（16KB 内存、2 次迭代、1 并行度、32B 输出）
  • Nonce：salt 的前 12 字节（确定性，无需单独存储）
  • 算法：ChaCha20 对称流密码
  • 压缩：zstd level 3

版本兼容

版本最小文件区别
v0x000140B (header 8 + hash 32)无 salt 区
v0x000256B (header 8 + salt 16 + hash 32)新增 16B salt 区

五大查询

三大核心查询 + 两项扩展方法 + 辅助算法 + 跨字段查询。

图 9: 查询系统 — 核心 / 扩展 / 辅助 / 跨字段
查询回答什么问题算法复杂度
traverse(from, relation?)这个节点连接到什么？直接邻接查找O(1)
impact(nodeId)如果这个变了，谁受影响？反向 BFSO(V+E)
path(from, to)怎么从 A 到 B？BFS 最短路径O(V+E)
subgraph(seeds, depth, relation?)子生态系统长什么样？BFS 提取O(V+E)
validate()图内部一致吗？结构检查O(E)

重要纠偏：POSITIONING_7_25.md 明确指出内核查询面固定为三个原语：traverse、impact、path。subgraph 和 validate 是这三个的组合或工具，不是第四、第五个"核心查询"。

跨字段查询

  • traverse_across_fields：递归进入目标 Field，visited 防循环
  • impact_across_fields：遍历所有 Field 的 incoming，Bridge 自动跟随
  • path_across_fields：BFS 状态含 current_field，field_path 记录路径

辅助算法

  • centrality(limit)：度中心性（in + out degree），降序 top-N
  • reachable(from)：传递闭包 BFS，返回所有可达节点
  • health()：孤儿/源/汇/连通分量统计

跨字段桥接机制

Bridge 是 Field 之间的双向连接，使查询可以自动跨越 Field 边界。

图 10: 桥接机制 — 双向创建 + 跨字段查询 + 四层验证

Bridge 创建流程

  1. 验证两个 Field 和两个 Node 都存在
  2. 创建两条边：forward（存入 from_field）和 reverse（存入 to_field）
  3. 两条边都设置 target_field 指向对方字段，relation = Bridges
  4. 同时存入 Cluster 级别的 bridges 注册表
  5. ID 格式：bridge-{from_field}-{source}-{to_field}-{target}-fwd/rev

Cluster 四层验证

层级检查内容严重度
Field 级孤儿边（source/target 不存在）Error
外部节点边引用不在 Cluster 注册表中Error
断裂桥接Bridge 的 target_field 指向不存在的 FieldError
孤儿节点注册但不在任何 Field 中Warning

四阶段交互

Phase 1: 注入层

Agent 启动前注入拓扑上下文。权重感知：≥0.8 强制包含，0.5-0.8 有条件，<0.5 按需。ACE Delta 增量更新。

Phase 2: 运行时查询

6 个查询映射为 MCP 工具：traverse/impact/path/subgraph/validate/diff。结构化契约，非自然语言。

Phase 3: 回写同步

Agent 不直接修改 Cluster，通过 diff → syn 提案 → 合并流程。SynProposal 生命周期：Draft → UnderReview → Approved/Rejected → Implemented。

Phase 4: Multi-Agent

三层架构：Swarm → Coordinator → Subagent。DAG 任务图调度。分级错误：Abort/Skip/Retry/Fallback。

未解决问题

存储与序列化

  • 加密密钥管理：当前密码通过 CLI 参数明文传入，不安全。可能方案：环境变量、密钥文件、系统密钥链
  • 大文件处理：当前全量读写，无流式处理。大 Cluster（>100MB）可能内存溢出
  • 加密/压缩端到端验证：代码已实现但尚未进行完整前端验证

共享与合并

  • 跨 Cluster 引用：未实现。每个 Cluster 完全独立
  • 三路合并：当前是"两路"合并，缺少共同祖先
  • 惰性克隆：当前 Clone 是全量深拷贝 O(n)
  • 合并时密码验证：源 Cluster 有密码时是否要求验证？未实现

查询与算法

  • 路径查询索引：长路径（>100 节点）BFS 效率可能不足
  • Impact 查询精度：当前简单反向 BFS，未考虑边类型和深度限制
  • blast_radius：当前为空 Vec，未实现
  • 子图查询性能边界：大图深度无限制时未做基准测试

表征层与 Agent 交互

  • niche/SYN/Arrow Map 占位 crate：已创建为占位符，编译通过，无功能逻辑

硬规则

来源：AGENTS.md（权威来源，与 knowledge-base 冲突时以 AGENTS.md 为准）

身份规则

  • Statuz 不是传输协议、不替代 MCP、不实现 A2A（A2A 字段是预留占位符）

范式规则

  • 不添加 YAML 文件（旧范式已死）
  • 不复活 niche/SYN/Arrow Map 文件格式
  • 表示层 crate 不得创建独立存储/CLI/Schema/序列化
  • 不添加 CLI 命令在 Engine 稳固之前
  • 不添加数据库、服务器、网络调用

质量规则

  • self-test 必须在每次变更后通过
  • 代码语言必须是英文
  • 零非 serde 依赖（图算法用 std 集合）
  • 内存优先，序列化是快照
  • 无 unwrap() 在库代码中
  • 无未使用变量或导入

存储规则

  • Cluster 是唯一存储单元
  • 存储格式不可变（magic + version 不能更改）
  • 内容可寻址（blake3）
