## 0. 问题是什么（为什么它值得单独一份）

不把 Field 类型化当成"给 Field 加一个 `type: String`"。那是两行字段的答案。

真正的问题是：**一个语义子图（Field）如何在真实项目中随项目"活着"——何时出生、何时变更、谁触发、如何保证里面装的信息是对的。** 它接上 Statuz 的图 Loop 与主动释放：field 的诞生与更迭不该靠人手写，而该由状态演化驱动。

这决定 Statuz 是"能存一张图的漂亮盒子"，还是"agent 时代的语义状态底座"。

---

## 1. 「被声明 vs 被发现」的分叉判断 → 已裁定

场景：Field 从哪来？

- **A. 被声明（top-down）**：类型预定义，field 由人/agent 显式宣告再填。像数据库建表。
- **B. 被发现（bottom-up）**：系统从真实项目自动识别聚集区并贴类型。
- **C. 混合 = 发现生成 + 声明定型**：系统先发现一块"语义自洽的聚集区"，再由人/agent 用类型赋型。发现负责"它该存在"，声明负责"它是什么"。

**裁定（2026-08-21）：C。** 系统先发现聚集；人在不确定时定型。

---

## 2. 「何时动用人类的裁定」→ 已裁定

- **系统不确定时，通过 SYN 机制推给用户排忧。**（见 §4：SYN 地基已存在。）
- 进一步裁定 **少打扰优先**：只有候选聚集到类型归属「明显张一认识」时才动用 SYN（例如一个聚集区同时象"战略"又象"架构"，或它跨了多个用户亲手建的关键 field）；其余静默定型。

**反面是被否掉的方案**："宁可错降，也要多问"——凡是类型归属非 100% 确定都推复核。被否理由：会把用户淹没在 SYN 提案，等于系统把工作外包，而非长大。

## 3. 尝试把四段生命周期写成链

```
① 发现  系统扫描项目，识别"节点聚成一团且语义自洽"的聚集区 → 候选 field
② 置信  评估候选的类型归属 / 边界，给一个确定性
③ 决策  把握大 → 直接定型；不确定 → 生成 SYN 提案推给用户
④ 维持  项目演化导致 field 失真 → 变更 / 重定型（规则仍待定）
```

## 4. 已知可用的地基（无需新建）

- `SynProposal`：id / summary / description / options / diff / audit_trail / status / created_at
- `SynStatus`：Draft → UnderReview → Approved → Rejected → Implemented
- `SynOption`：label / description / merge_strategy（"skip"/"overwrite"/"rename"/"merge_meta"）
- 均已在 `crates/statuz-core/src/graph/types.rs` 中完整实现。
- →「不确定就推给用户」的**决策走廊地基已经存在**，方向无须从零搭。
